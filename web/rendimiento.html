En GitHub abre la pestaña Actions, elige Rendimiento (speedup) y presiona Run workflow. Mide los juegos del repo en modo secuencial y con 1, 2, 4, 8, 16 y 32 hilos; tarda cerca de una hora y esta página se llena sola.

También se puede medir en una computadora con rendimiento.bat.

Mediciones

Speedup = tiempo secuencial ÷ tiempo con N hilos. La eficiencia y Karp–Flatt se calculan sobre el nivel 1, tomando 1 hilo como base.

Ley de Amdahl

Si una fracción f del trabajo no se puede repartir entre hilos, el speedup con p hilos es

S(p) = 1 / ( f + (1 − f) / p )

y nunca puede pasar de 1 / f, aunque se agreguen más hilos.

¿De dónde sale la parte secuencial en este programa?

  • Preparación: leer la lista de juegos del repo en Firestore antes de empezar (unos segundos). Se hace una sola vez.
  • Límite por sitio: a cada tienda se le hacen como máximo 4 peticiones a la vez (a Amazon 2, con una pausa) para no ser bloqueados. Con muchos hilos, los juegos hacen fila para el mismo sitio y esa fila se comporta como trabajo secuencial.
  • La última ronda: cuando quedan pocos juegos, los más lentos terminan solos y varios hilos se quedan sin trabajo.
  • La red y los propios sitios: cuánto tarda cada página en responder no depende de nuestros hilos.

Dos cosas que se ven en las mediciones

  • Con 1 hilo ya es más rápido que la versión secuencial: aunque el nivel 1 procese un juego a la vez, los niveles 2 y 3 consultan sus fuentes y sus tiendas en paralelo.
  • El speedup puede superar el número de núcleos. El trabajo consiste casi todo en esperar respuestas de red: con async/await un núcleo atiende muchas peticiones a la vez, así que los hilos compiten por los sitios, no por el procesador.

Cómo se midió

  • Todas las configuraciones procesan los mismos juegos del repo, con todas las tiendas, Metacritic y HowLongToBeat.
  • No se usan resultados anteriores: cada corrida hace el trabajo completo.
  • Cada configuración empieza con un cliente HTTP nuevo y un calentamiento de 3 juegos que no se mide.
  • El tiempo es el del scraping; la lectura del repo se informa aparte como parte secuencial.
  • En GitHub Actions cada configuración corre en su propio servidor y al mismo tiempo, para que ninguna herede bloqueos o límites de peticiones de otra.
  • Los sitios responden más rápido o más lento según la hora, así que hay algo de variación entre corridas.
